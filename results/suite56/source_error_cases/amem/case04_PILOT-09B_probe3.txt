Assistant: A good middle ground is to adopt numbered, forward-only migrations plus a tiny metadata table for applied versions. Keep each change in its own file, for example:

- `001_init_schema.sql`
- `002_add_audit_columns.sql`
- `003_backfill_status.sql`

Then have your migration runner:
1. create a `schema_migrations` table if it doesn't exist
2. check which versions have already been applied
3. run pending files in order
4. record version, checksum, and applied timestamp

You can also separate:
- **DDL migrations** for structure changes
- **data migrations** for backfills/recomputations
- **repeatable scripts** for views or derived objects

A simple repo layout could be:

```text
db/
  migrations/
    001_init_schema.sql
    002_add_audit_columns.sql
  data/
    003_backfill_status.sql
  scripts/
    verify_checksums.sh
```

CREATE TABLE IF NOT EXISTS schema_migrations (
